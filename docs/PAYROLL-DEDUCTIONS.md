# Matesther payroll deductions — operational and deployment notes

## Reused instead of replaced

- Next.js 16 App Router + Drizzle/PostgreSQL; the Owner/Project Manager/Worker session guard and same-origin write protection remain in force.
- `lib/payroll.ts` still calculates salary, approved production pieces and approved support work; the helper's rate still comes **out of the tailor's piece rate**, not out of salary or a second company deduction. `worker_payments` is still an append-only record of cash paid, not a deduction ledger. The monthly bank sheet and 12-month payroll history remain.
- Workers already have `department`, multi-role employment categories, `MONTHLY` and `PER_PIECE` (and the existing, non-accruing `DAILY` profile type). Inspection rows and support approvals are immutable evidence; rejected/rework pieces do not generate pay or a fine. There was **no** general deduction table, attendance register, cooperative balance or tax engine to reuse.
- `HYBRID` adds salary **plus** approved production/support piecework to a *new, unused* worker profile. It does not reinterpret existing profile types. Changing an established worker into/out of HYBRID is rejected: earlier inspections and salary have no effective-dated contract snapshot in the legacy schema. This needs a separately approved contract-versioning design before in-place conversion can be made safe.

## Storage and why it is needed

The existing `worker_payments` columns describe positive *cash* settlements, `worker_overtime` describes positive approved *earnings*, and `stage_inspections` describes production quality/approved piecework. None can safely represent individually authorised deduction terms, recurring schedules, reviewed attendance/damage cases, a posted tax/coop ledger and a preserved decision trail. Reusing any as a negative amount would corrupt revenue/cost or the inspection audit. Therefore migration `drizzle/0013_payroll-deductions.sql` adds **seven empty tables only**:

| Table | Purpose |
| --- | --- |
| `payroll_deduction_categories` | Owner-managed *custom* categories; built-in statutory/absence/damage/savings types stay protected in code. |
| `payroll_attendance` | One *explicit* situation per worker/day, with evidence and correction audit; no time-clock inference. |
| `payroll_deductions` | One immutable set of terms per worker (including each worker in a bulk request), status/actor/consent, period and incident/assessment evidence. Correct by cancelling unposted terms and proposing new terms. |
| `payroll_deduction_audit` | Append-only actor/time/reason and before/after for every category, day, proposal, review, reversal and posting decision. |
| `payroll_statements` | **Immutable worker/period snapshot** of approved earnings, old support allocation, statutory withholding, other deductions and net. One per worker/month. |
| `payroll_statement_lines` | Itemised posted deduction or signed compensating refund. `cooperative_credit` on a posted line **is the transaction ledger**; balance is the sum, never an independently mutable balance. |
| `payroll_reversals` | Independent review of a **full** refund of a posted non-tax line in a later period. No old statement is rewritten. |

Constraints include case-reference uniqueness per worker, one statement per worker/month, one posting of each proposal/refund, active-only uniqueness of attendance/**stage or support** inspection cases, and a constraint matching cooperative credit to its line amount. Separate foreign keys and unique indexes distinguish stage inspections from support-work inspections even when their numeric IDs overlap. References to inspections protect their history; financial workers are archived, not deleted. Posted statements snapshot worker name and department so reports do not regroup history when a profile changes. Audit names survive account deletion. New endpoints always scope to the session's organisation and Owner role; no financial parameters from the request body override the actor or organisation. The new UI uses paginated worker searches; bulk eligibility is resolved again on the server under worker locks.

The migration is additive and re-runnable in PostgreSQL. It inserts **no data**, never mutates existing wage/production/expense rows, and has a matching manually runnable transaction script at `deploy/upgrade-payroll-deductions.sql`. **Use the hand-run SQL Editor script for Supabase**, not `drizzle-kit migrate`: unlike the schema-only Drizzle migration, the hand-run script also enables RLS on all seven new tables and revokes table and sequence access from `anon`, `authenticated` and `PUBLIC` before commit. The Next.js server uses the existing trusted database role and continues to enforce Owner/organisation checks. Verify this role can read/write on staging while direct REST roles cannot. Apply SQL **before deploying** code; Netlify does not migrate Supabase automatically. `deploy/rollback-payroll-deductions.sql` can remove **only empty** new tables. Once anything is posted, rollback **code only**, leaving the financial trail untouched. Validate on a staging **real PostgreSQL** clone first: the automated tests use pg-mem, which cannot prove PostgreSQL isolation or actual SQL Editor behavior.

## Authorization, legality and calculation

1. An Owner creates a **PENDING** per-worker proposal. `HOUSE_RENT`, `COOPERATIVE`, `STAFF_OCCASION` and custom categories require **each worker's** written consent reference/date and an authorising agreement/scheme reference. A group/all selection has no implicit consent: every member needs their own entry. `VARIABLE`, custom, absence, tax and damage proposals, and every refund, need approval from a **different Owner account**. A Project Manager/Worker may not read or write these endpoints, even by direct API request.
2. One-time, monthly or every 2–12 months are supported, with start/end payroll months. Percentages use integer basis points (100 = 1%); calculation rounds **once** to whole naira. Attendance amount = monthly salary ÷ Owner-documented policy working days, rounded once. Only an explicitly recorded `UNAUTHORIZED_ABSENCE` or `UNPAID_LEAVE` may be proposed; `PRESENT`, `PAID_LEAVE`, `APPROVED_LEAVE`, `OTHER` and missing days are **not** deductions. No attendance fine is inferred from timesheets that the ERP does not have. `DAILY` profiles have no monthly-salary base and cannot have an attendance deduction here.
3. A damage case must link **exactly one rejected stage or support-work inspection** for that worker, on an identified garment/order, and a quantity no greater than its rejected count. The Owner must document findings of wilful neglect/misconduct, the **remaining net loss after pay withheld on rejected stage/support pieces**, and *prior written labour-officer consent*. The case amount cannot exceed that remaining loss, and damage cases are **one-time only**: recurring the same incident could exceed proven loss. An installment design needs separate legal review, not a repeated automatic charge. Rework or an unsuccessful inspection alone never produces a charge. Support and stage IDs have separate sequences and are never interchangeable. No production/support inspection or movement is changed by a payroll case.
4. PAYE is a **separate statutory category**, not a custom percent. The only automated schedule is the enacted **Nigeria Tax Act 2025**, applicable from **1 January 2026** (section 58, Fourth Schedule, sections 30–32): annual chargeable-income bands ₦800,000 @ 0%, next ₦2.2m @ 15%, next ₦9m @ 18%, next ₦13m @ 21%, next ₦25m @ 23%, above ₦50m @ 25%. Actual paid annual rent relief = 20%, capped at ₦500,000; verified pension, NHF, NHIS and specifically documented other statutory reliefs are subtracted from assessed annual gross. The signed worker assessment (including evidence for the statutory minimum-wage exemption, where applicable) must be individually created and independently approved. Monthly PAYE = progressive annual liability / 12, rounded to whole naira; no flat tax is imposed on every worker and variable production income is **not** blindly annualized. This module does **not** compute 2025 or future-year PAYE without a reviewed new legal schedule. Source: [Nigeria Tax Act official gazette](https://nass.gov.ng/documents/download/11249); [Federal Ministry of Finance transition guidelines](https://finance.gov.ng/federal-government-issues-transition-guidelines-for-tax-acts-2025/).
5. On preview, the current approved earnings (including support piecework, *after* existing helper allocation) are calculated first. Approved tax + ordinary deductions must be **at most the actual available earnings** and, conservatively, **at most one-third** of the worker's earned pay in that month. No auto-clamping, silent carry-forward, or application to unapproved output: if anything exceeds either ceiling, posting is blocked and the Owner must correct terms/reschedule or seek legal advice. The support-work rate split is not a second employer fine/deduction; it retains its original piece-earnings-only cap/carry rule. This conservative treatment of the Labour Act section 5(7) ceiling (including statutory items) requires local payroll/legal sign-off. Section 5(1) addresses prior labour-officer consent for willful injury/loss; section 5(2) addresses agreed, State-approved provident/other schemes. Source: [Labour Act text](https://nelex.gov.ng/documents/LABOUR_ACT.pdf).
6. Posting is allowed **only after the month is complete**, for a worker/month with no recorded cash payment. The Owner reviews gross, each item, legal issues and net, then posts in **one transaction under a worker row lock**. That books each cooperative credit once. A current-month preview is not final; payment creation and the bank sheet refuse unposted approved deductions. Periods already paid or posted cannot acquire retroactive deductions. A prior unprocessed month is allowed only with an explicit late-entry reason; months earlier than the immediately previous month require a separate reviewed correction policy. Ordinary months without new deductions retain the old cash-payment workflow.
7. Cancel an unposted proposal with a reason and re-propose corrected terms. Cancelling an approved proposal after posting stops it **in future periods only**; the posted statement stays. A posted **non-tax** mistake can be fully refunded in a later payroll period via a new independently approved negative line (including a negative cooperative credit). No direct edits or deletion of posted money. PAYE corrections/remittance/refunds need review with the relevant tax authority; a company refund cannot masquerade as a tax correction.

**Operational sign-off needed:** A reference field is *not* verification of the actual signature, statutory scheme approval, labour-officer letter, rent receipt or tax classification. Owners must check and retain the real documents outside the ERP. Confirm Labour Act scope/ceiling and applicable tax status with Nigerian payroll/legal advisers **before enabling live deductions**, and arrange tax remittance and cooperative fund custody/reconciliation; this ERP records deductions/credits but does not remit tax or manage cooperative withdrawals. If Matesther has daily workers with a separate wage rule, that rule needs specification before calculating their attendance/pay; existing `DAILY` currently accrues no monthly salary. An effective-dated contract history for existing-worker HYBRID conversions and partial posted refunds are likewise future decisions, not silently guessed here.

## Verify in the ERP (staging, no production financial records)

1. Apply `deploy/upgrade-payroll-deductions.sql` to a **staging/client** database after a backup. Its verification rows should show all seven new tables and zero records before use, RLS enabled on each, and both inspection-ID columns present. Verify the trusted server DB role can still access the tables and `anon`/`authenticated` cannot. Do **not** run `seed.sql`, `drizzle-kit migrate` or `deploy/full-setup.sql` against a live client database.
2. Sign in as Owner → **Finance → Payroll Deductions**. Create a custom category or use a built-in one. Select one or several active workers, or preview a department/category/all group; supply a *different actual consent reference for each worker* where required. Verify status **PENDING** and that payroll is unchanged.
3. A second Owner reviews exceptional cases (tax, damage, absence, variable/custom, refund). See **Records** and **Audit**. Use **Attendance** to record a documented day. For a damage case, choose a rejected **stage or support-work** inspection for the responsible worker (or specify its source and ID if older than the 100 most recent); verify the documented net loss and prior authorisation. Neither an attendance row nor an inspection creates an automatic deduction.
4. Under **Payroll review**, choose a worker and a **completed, unpaid** month. Inspect gross, helper allocation, each item, one-third warnings and net; post only when correct. The printed **Bank Payment Sheet** will refuse an unposted deduction. Back under **Worker Payments**, verify gross/deduction/net, status and payment history; record only the remaining **net** cash payment. **Reports** filters posted lines by period/category/department/worker; **Cooperative** shows credited history and balance.
5. To correct a posted non-tax mistake, request a full refund from the posted item and ask a different Owner to approve it. When its later month closes, post that period; the original period and its audit stay intact, and the cooperative balance receives the matching debit.

Automated verification: `npm test` runs on an empty in-memory database using the real migrations and route handlers. `npm run typecheck`, `npm run lint` and `DATABASE_URL=postgresql://build:build@127.0.0.1:5432/unused_build npm run build` (the build **does not connect** to that dummy database) check code. Before production: repeat migration + concurrency/transaction tests on a **real staging PostgreSQL** database, then have payroll/legal reviewers sign off the assessment and evidence rules.
